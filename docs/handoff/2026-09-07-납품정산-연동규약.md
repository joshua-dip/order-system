# 납품 정산 연동 규약

**웹앱 → 제작기** · 2026-09-07 · 「납품 정산 기록 스펙」(제작기, 2026-09-07)에 대한 회신

스펙 05-5 「무료 한도를 deliveredCount 기준으로」는 웹앱 쪽에 반영해 배포했다.
다만 **총 부족분만으로는 한도를 정확히 되돌릴 수 없다** — 한도는 전체 문항이 아니라
유료 기본난도만 세기 때문이다. 유형별 내역 하나만 더 넣어 주면 정확해진다.

---

## 웹앱이 읽는 필드 〈반영 완료〉

`/api/my/variant-base-quota` 가 이번 달 주문을 합산할 때 `orders.delivery` 를 함께 읽는다.
아래 두 필드만 계산에 쓰고 나머지는 건드리지 않는다.

| 필드 | 우선 | 웹앱 동작 |
|---|---|---|
| `delivery.shortfallByType` | 1 | 유료 기본난도 유형의 부족분만 골라 한도에서 뺀다. **정확.** |
| `delivery.shortfall` | 2 | 총량을 그대로 뺀다. 무료 유형 부족까지 돌려주게 되지만 고객에게 불리하지 않은 쪽. |
| 그 외 `delivery.*` | — | 한도 계산에 쓰지 않음. 관리자 표시용으로만 읽을 예정. |

워크북(`BW`·`MW`)은 문항 개념이 없어 한도와 무관하다. `passageCount` 만 채워도 웹앱 계산에는 영향이 없다.
취소 주문은 웹앱이 집계에서 제외하므로, 제작기 쪽에서 취소분 `delivery` 를 지울 필요는 없다.

---

## 왜 총량만으로는 틀리는가 〈제작기 요청〉

한도를 쓰는 것은 **유료 기본난도**뿐이다.
무료 7종(주제·제목·주장·일치·불일치·순서·삽입)은 회원 여부와 무관하게 0원이라 처음부터 한도를 쓰지 않고,
고난도(80원)는 한도 대상 밖이다. 스펙 01의 사례를 그대로 풀면 이렇게 갈린다.

| BV-20260907-002 부족분 | 유형 성격 | 문항 | 한도 반환 |
|---|---|---:|---:|
| 순서 | 무료 7종 — 한도를 쓰지 않음 | 17 | 0 |
| 어휘 | 유료 기본난도 — 한도 대상 | 3 | **3** |
| **합계** | | **20** | **3** |

`shortfall: 20` 만 오면 웹앱은 20을 되돌린다 — 실제로 돌려줄 것은 3문항이므로
**17문항이 과잉 환급**된다. 고객에게 손해는 없지만 한도 장부가 조용히 어긋난다.

### 요청 — 필드 하나

`orders.delivery` 에 유형별 부족 내역을 같이 넣어 주면 웹앱이 정확히 처리한다.

```js
// orders.<주문>.delivery — 기존 스펙 03 에 한 줄 추가
{
  orderedCount:    468,
  deliveredCount:  448,
  shortfall:       20,
  shortfallByType: { "순서": 17, "어휘": 3 },   // ← 추가
  shortfallReason: "지문이 짧아 순서 17·어휘 3 불가",
  …
}
```

키는 주문서의 유형명을 그대로 쓴다(`orderMeta.selectedTypes` 와 같은 문자열).
웹앱이 무료·고난도 유형을 스스로 걸러내므로 **전 유형을 다 넣어도 된다**.
`shortfallReason` 은 사람이 읽는 용도로 그대로 두면 된다.

## 연동하다 드러난 버그 둘 〈웹앱 고침〉

### 모의고사 주문이 한도에 거의 안 잡히고 있었다

`paidBaseCountOf` 가 지문 수를 `selectedLessons` 에서만 읽었다.
모의고사(MV)는 번호가 `examSelections[].numbers` 에 있어 지문 수가 통째로 빠졌고,
한도가 사실상 무제한처럼 동작했다.

> 이번 달 한 회원 집계 **24문항 → 432문항** (18배)

스펙 04 표의 flow 별 분기와 같은 취지다.
`"41~42번"` 은 지문 하나이므로 배열 길이를 쓰고 하이픈을 쪼개지 않는다.

### 취소한 주문이 한도를 계속 묶고 있었다

집계 쿼리에 상태 조건이 없어, 주문을 취소해도 그 주문이 쓴 문항이 한도에서 풀리지 않았다.
`status: { $ne: 'cancelled' }` 를 넣었다.

> 박미란 · MV-20260907-003 취소 후 **34문항** 반환

## 메일 발송 기록 〈제작기 확인 요청〉

관리자 주문 목록에 **「메일」 열**을 붙였다(완료일 왼쪽). 보낸 건은 Resend 대시보드
`https://resend.com/emails/<id>` 로 링크되어 본문·전달 상태를 열어볼 수 있다.

실제 자료 메일은 제작기에서 나가므로, 웹앱 자체 발송 기록이 없으면
**`delivery.emailIds` 의 마지막 값과 `delivery.sentAt` 을 읽어** 「✉ 발송 · 제작기」로 표시한다.
`sentAt` 이 없어도 `emailIds` 만 있으면 발송으로 본다.

확인해 줄 것 세 가지.

1. **`emailIds` 에 넣는 값이 Resend 의 message id 가 맞는지.**
   `resend.emails.send()` 응답의 `data.id` (예: `573ed756-…` UUID 형태).
2. **Resend 계정이 웹앱과 같은지.**
   대시보드 링크는 로그인한 계정의 메일만 열린다. 제작기가 다른 API 키·다른 계정을 쓰면
   링크가 404 가 되므로, 그때는 링크를 걸지 않도록 웹앱 쪽을 바꾸겠다.
   (웹앱은 `RESEND_API_KEY` · `RESEND_FROM_EMAIL` 환경변수를 쓴다)
3. **여러 번 보낸 경우 `emailIds` 를 배열 끝에 덧붙이는지.**
   웹앱은 마지막 원소를 「가장 최근 발송」으로 보고 대표 링크로 쓴다.

## 남은 것

- **부족분 포인트 환불** — 유료 문항이 못 나갔을 때 환불액을 계산해 포인트로 돌려주는 흐름은
  웹앱 쪽에 아직 없다. `shortfallByType` 이 들어오면 유형별 단가(무료 7종 0원 · 기본 50원 ·
  고난도 80원)에 볼륨 할인율을 곱해 자동 산출할 수 있다.
- **관리자 목록 표시** — 주문 목록에 납품·부족을 띄우는 열은 아직 없다.
  `delivery` 가 채워지기 시작하면 붙인다.
- **소급 범위** — 스펙 06 대로 근거 있는 38건만. 근거 없는 149건은 비워 두는 판단에 동의한다.
  추정값이 들어가면 한도 계산이 조용히 틀린다.
