## A. 규약을 어긴 것

### A1. 순서 문항이 답을 드러냈다 — 9문항 (가장 심각)

`(A)(B)(C)` 블록을 **정답 차례대로** 출력했다. 위에서 아래로 읽으면 그게 답이다.

```
168192  본문 차례 (A)→(C)→(B)   정답 ① (A)-(C)-(B)
168258  본문 차례 (A)→(C)→(B)   정답 ①
168291  본문 차례 (B)→(A)→(C)   정답 ②
```

**규칙: 블록은 언제나 `(A)` → `(B)` → `(C)` 라벨 차례로 출력한다.** 정답은 라벨 순열로만 나타낸다.
자가 점검 — 본문에 나오는 라벨 차례가 A,B,C 가 아니면 잘못 만든 것이다.

### A2. 같은 지문·같은 유형에서 정답 번호가 겹쳤다 — 171지문

한 지문의 같은 유형 3문항은 정답 번호가 서로 달라야 한다. 겹친 지문 수(전체 39지문 기준):

```
일치 31 · 제목 29 · 주장 28 · 빈칸 25 · 함의 22 · 요약 20 · 주제 15 · 불일치 15
순서 0 · 삽입 0 · 어휘 0   ← 이 세 유형은 잘 돌렸다
```

원인은 아마 **저장 경로**다. 규약([정답 위치 분포](../variant/AUTHORING.md#정답-위치-분포))은 셔플 O 유형(빈칸·요약·함의 등)을
저장 시 `shuffleQuestionDataForDistribution` 가 섞어 준다고 전제한다. kimi 는 웹앱을 거치지 않고 Mongo 에 직접 넣어
그 셔플이 걸리지 않았다. **웹앱 저장 경로를 쓰거나, 직접 넣을 거면 같은 분산을 kimi 쪽에서 해야 한다.**

### A3. 순서 보기를 `###` 로 구분했다 — 117문항

규약: 순서 Options 는 **줄바꿈 구분**이다. 관리자 검증기(`app/api/admin/generated-questions/validate/order-options`)가
`\n` 으로만 쪼개 길이 5를 보기 때문에, `###` 로 넣으면 길이 1로 읽혀 「수정 대상」이 된다.

```
잘못  "① (A)-(C)-(B) ### ② (B)-(A)-(C) ### …"
맞음  "① (A)-(C)-(B)\n② (B)-(A)-(C)\n③ (B)-(C)-(A)\n④ (C)-(A)-(B)\n⑤ (C)-(B)-(A)"
```

### A4. 지문을 고쳐 썼다 — 함의 167918

원문 `Timothy's eyes opened wide` 를 `his eyes opened wide` 로 바꿔 놨다.
밑줄 구간이라도 **지문은 원문 그대로** 두고, 손대는 것은 보기와 해설뿐이다.

### A5. 해설의 원문자 뒤 조사 — 630건

`③ 가 정답입니다`처럼 ①③ 뒤에 '가'를 썼다. 받침에 맞춰야 한다.

```
①(일) ③(삼) → 은 / 이 / 을 / 과      ①이 정답이다 · ③은 · ①과
②(이) ④(사) ⑤(오) → 는 / 가 / 를 / 와  ②가 정답이다 · ④는 · ⑤와
```

원문자와 조사는 **붙여 쓴다**(`④가`). 이 예시는 규약 문서에도 틀린 채 있다 — B4 를 볼 것.

## B. 규약대로 했는데 실제 납품 데이터와 어긋나는 것

**kimi 잘못이 아니다.** 규약 문서와, 제작기가 실제로 납품해 온 데이터가 서로 다르다. 이번 납품은 기존 고객이 받아 온
모양을 유지하려고 **실데이터 쪽으로 맞췄다.** 어느 쪽을 표준으로 삼을지 정해서 규약 문서를 고치면 좋겠다.

| 항목 | 규약(AUTHORING.md) | 기존 납품 데이터 · 제작기 | 이번 조치 |
| --- | --- | --- | --- |
| B1 삽입 지문 구분 | 주어진 문장 + **빈 줄** + 본문 | `주어진문장\n###\n본문` | 데이터 쪽으로 (117건) |
| B2 빈칸 표시 | `<u>_____</u>` (5칸) | `<u>` + 밑줄 **50칸** | 데이터 쪽으로 (117건) |
| B3 요약 보기 | `(A) word - (B) word` | `word - word` (라벨 없음) | 데이터 쪽으로 (117건) |
| B4 해설 예시 | `"③ 가 정답입니다. …"` | `③이 정답이다` | 규약 예시가 틀렸다 |
| B5 status | `"대기"` | 제작기는 `"완료"` 만 조회 | 아래 참고 |

- **B1·B2**: 제작기는 `Paragraph` 의 줄바꿈을 `###` 로 바꿔 문단을 나눈다(`변형문제제작기_DB._paragraph_from_db`).
  빈 줄이면 문단 간격이 기존 납품물과 달라지고, 밑줄 5칸은 인쇄물에서 눈에 띄게 짧다.
- **B4**: 규약의 스키마 예시가 `"③ 가 정답입니다"` 라서 1,287건이 그대로 따라 왔다. 예시부터 `"③이 정답입니다"` 로 고쳐야 한다.
- **B5**: 제작기(`변형문제제작기_DB.db_load_questions`)는 `status: "완료"` 만 불러온다. `"대기"` 로 넣으면 웹 관리자에는 보여도
  **주문 제작에는 잡히지 않는다.** 사람 검수를 거칠 문항이면 `"대기"`, 바로 납품에 쓸 문항이면 `"완료"` —
  어느 쪽인지 정해서 알려 주면 제작기 쪽에서 맞춘다. (이번 1,287건은 `"완료"` 로 들어왔고, 167009 한 건만 `"대기"` 였다.)
- 참고: `error_msg` 에 문자열 `"None"` 이 들어온 건이 있었다. 비우려면 빈 문자열로 둘 것.

## C. 규약에 없어 어긋난 것 — 관행

### C1. 유형별 표준 발문 — 462문항이 달랐다

기존 문항 다수가 쓰는 문장이다. 그대로 쓰면 된다.

| 유형 | 표준 발문 |
| --- | --- |
| 주제 | 다음 글의 주제로 가장 적절한 것은? |
| 제목 | 다음 글의 제목으로 가장 적절한 것은? |
| 주장 | 다음 글이 주장하는 바로 가장 적절한 것은? |
| 함의 | 밑줄 친 부분이 다음 글에서 의미하는 바로 가장 적절한 것은? |
| 빈칸 | 다음 글의 빈칸에 들어갈 말로 가장 적절한 것은? |
| 요약 | 다음 글의 내용을 한 문장으로 요약하고자 한다. 빈칸 (A), (B)에 들어갈 말로 가장 적절한 것은? |
| 일치 | 다음 글의 내용과 일치하는 것은? |
| 불일치 | 다음 글의 내용과 일치하지 않는 것은? |
| 어휘 | 다음 글의 밑줄 친 부분 중, 문맥상 낱말의 쓰임이 적절하지 않은 것은? |
| 순서 | 주어진 글 다음에 이어질 글의 순서로 가장 적절한 것을 고르시오. |
| 삽입 | 글의 흐름으로 보아, 주어진 문장이 들어가기에 가장 적절한 곳을 고르시오. |

kimi 는 함의 발문에 밑줄 친 표현을 따옴표로 옮겨 적었다(`밑줄 친 "…" 표현이 …`). 지문에 `<u>` 밑줄이 있으면 위 표준 문장을 쓴다.

### C2. 유형별 정답 번호 분포 — 한 번호 40% 미만, 목표는 각 20% 안팎

| 유형 | kimi 생성분 | 제작기가 고친 뒤 |

| 순서 | ① 5(4%) · ④ 33 · ⑤ 35 | ① 18(15%) · ③ 28 · ⑤ 25 |
| 어휘 | ① 8(7%) · ⑤ 36(31%) | **그대로 — 고칠 수 없음** |
| 삽입 | ① 16(14%) · ⑤ 32(27%) | **그대로 — 고칠 수 없음** |
| 나머지 8유형 | 최대 29% | 모두 20~21% |

**어휘·삽입·어법·무관한문장은 만든 뒤에 정답 번호를 못 옮긴다.** 본문에 밑줄·마커가 박혀 있어 보기를 맞바꾸면
본문과 어긋나 문항이 깨진다(제작기 `balance_sel.py` 의 `MARKER_ONLY`). **이 네 유형은 생성 단계에서 번호를 고르게 나눠야 한다.**
