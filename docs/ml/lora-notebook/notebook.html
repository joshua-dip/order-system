1과

모델 고르기 — Qwen, Llama, 그리고 "7B"

LLM 은 회사가 만들어 공개한 "오픈 모델"을 가져다 씁니다. 이름 뒤의 숫자는 모델의 크기입니다.

모델 안에는 파라미터라는 숫자가 잔뜩 들어 있습니다. 문장을 읽고 다음 단어를 고를 때 쓰는 "뇌세포" 같은 값이에요. 7B 의 B 는 billion(10억) — 파라미터가 약 70억 개라는 뜻입니다. 많을수록 글을 더 깊이 이해하지만, 메모리를 더 먹고 느려집니다.

Qwen(큐웬)은 알리바바, Llama(라마)는 메타가 만듭니다. Qwen 은 한국어 같은 아시아 언어를 많이 배워서, 한국어 해설이 들어가는 우리 문항에 더 잘 맞습니다.

2과

4bit 양자화 — 모델을 압축해서 올리기

파라미터 하나를 16칸짜리 숫자 대신 4칸짜리 숫자로 거칠게 적어서, 모델을 약 4분의 1로 줄입니다.

원래 파라미터 하나는 16bit(소수점까지 꽤 정밀한 숫자)로 저장됩니다. 이걸 4bit 로 반올림하면 정밀도는 조금 잃지만 크기가 확 줄어요. 모델 이름 끝의 -4bit 가 이 뜻입니다. 사진을 고화질 원본 대신 적당히 압축한 JPG 로 보내는 것과 비슷해요.

3과

학습 데이터 — "이렇게 답해"를 보여 주기

파인튜닝은 모범 답안 대화를 수천 개 보여 주며 형식과 판단을 가르치는 일입니다.

데이터 한 줄은 대화 세 칸으로 되어 있습니다. system 은 역할 설명, user 는 지문, assistant 는 우리가 원하는 정답(문항 JSON)이에요. 학습할 때는 assistant 칸만 채점합니다(--mask-prompt) — 지문을 외우는 게 아니라 "지문을 보면 이렇게 답한다"를 배우게 하려는 것입니다.

4과

LoRA — 모델 전체 대신 작은 부품만 가르치기

76억 개를 다 고치는 대신, 옆에 작은 부품을 붙여 그 부품만 학습합니다. LoRA 는 Low-Rank Adaptation, 「낮은 계수로 덧대는 적응」의 줄임말이에요.

원본 모델은 그대로 두고, 각 층에 얇은 보정판을 덧대는 방식이에요. 두꺼운 교과서를 새로 찍는 대신 포스트잇을 붙이는 셈입니다. 그래서 학습이 빠르고, 결과물은 포스트잇(어댑터)만 저장하면 됩니다. 원본과 합쳐서 써야 동작해요.

① 모델 안은 거대한 숫자표. 1과의 「파라미터 76억 개」는 사실 수백 장의 큰 숫자표(행렬)에 나뉘어 들어 있습니다. 단어 하나가 층을 지날 때마다 이 표들과 곱해지며 뜻이 다듬어져요. 우리 7B 모델(Qwen2.5-7B)은 28층이고, 한 층에 큰 표가 7장 있습니다 — 어텐션(8과 영상의 「심장」)에 4장, 그 뒤 지식을 담는 부분(피드포워드)에 3장. 예를 들어 어텐션의 한 표는 3,584 × 3,584 = 약 1,284만 칸입니다.

② 고칠 양을 두 개의 가느다란 표로. 보통의 파인튜닝은 이 1,284만 칸을 전부 조금씩 바꿉니다. LoRA 는 「바꿀 양」을 따로 두는데, 그걸 큰 표 하나로 두지 않고 가느다란 표 두 장(B × A)의 곱으로 표현해요. 폭(랭크, r)이 8이면 3,584 × 8 짜리와 8 × 3,584 짜리, 합쳐서 5만 7,344칸뿐입니다. 원래 표의 0.45%로 같은 크기의 「변화」를 만드는 거예요.

「낮은 계수(low rank)」는 이 폭 8을 말합니다. 3,584가지 방향으로 바꿀 수 있는 표를 8가지 방향으로만 바꾸게 제한하는 거예요. 우리가 가르치는 건 「수능 문항 JSON 모양으로 답하기」 같은 좁은 기술이라, 8가지 방향이면 충분합니다. 거꾸로 말하면 LoRA 로 새 지식을 많이 넣기는 어렵고, 이미 아는 걸 특정 모양으로 꺼내게 하는 데 강해요 — 9과에서 「형식은 LoRA, 독해는 큰 모델」로 나눈 이유가 이겁니다.

두 가지 잔재주가 있습니다. B 는 처음에 0으로 채워 두어서, 학습 시작 순간엔 모델이 원본과 똑같이 동작해요(망가진 채로 출발하지 않음). 그리고 곱한 결과에 스케일(우리는 20)을 곱해 보정판의 목소리 크기를 정합니다.

층당 72만 개는 표 7장의 보정판을 더한 값입니다: 어텐션 5만 7,344 × 2 + 3만 2,768 × 2(k·v 는 출력이 512로 좁다) + 피드포워드 18만 224 × 3. 숫자가 정확히 맞아떨어지는 걸 보면, 모델 속 「보이지 않는 부품」도 결국 이런 표들의 모음이라는 게 실감 납니다. 윈도우 PC 는 0.5B 를 400단계 학습하는 데 3시간 33분 걸렸습니다.

③ 어댑터는 갈아 끼우는 부품. 원본은 하나 두고, 유형마다 23MB 짜리 보정판만 따로 만들었습니다 — 주제·제목·주장·내용일치·빈칸 다섯 개(일치·불일치는 하나를 나눠 씀, 15과). 풀 파인튜닝이었다면 유형마다 15GB 짜리 모델이 따로 필요했을 거예요. 다만 보정판은 그 원본 전용입니다. Qwen 7B 에 맞춰 만든 어댑터는 Llama 나 35B 에 끼울 수 없어요 — 표의 크기와 모양이 다르니까요.

맥(MLX)에서는 어댑터마다 「원본 + 보정판」 모델을 한 벌씩 올려 두고 골라 씁니다(9과, 한 벌 4.3GB). 윈도우의 peft 는 원본 하나에 보정판을 여럿 붙였다 뗐다 할 수 있어 메모리를 덜 썼어요. 보정판을 원본에 아예 녹여(fuse) 한 모델로 만들면 조금 빨라지지만, 그러면 갈아 끼우기를 못 합니다.

5과

손실 곡선 — 학습이 잘 되고 있는지 보는 법

손실(loss)은 "모델의 답이 모범 답안과 얼마나 다른가"를 숫자로 잰 것입니다. 낮을수록 가깝습니다.

두 줄을 같이 봅니다. 학습 손실은 배운 문제에서의 점수, 검증 손실은 처음 보는 문제(확인용 348개)에서의 점수예요. 학습 손실은 계속 내려가는데 검증 손실이 다시 오르기 시작하면, 새로 이해하는 게 아니라 외우기 시작했다(과적합)는 신호입니다.

6과

사람이 채점하기 — 손실이 낮다고 정답을 맞히는 건 아니다

손실은 "말투와 형식이 모범 답안과 비슷한가"에 가깝습니다. 정답을 제대로 골랐는지는 따로 시험을 봐야 합니다.

그래서 시험 세트를 고정해 두고, 고칠 때마다 같은 시험을 봅니다. 확인용에서 서로 다른 지문 5개와, 실제로 틀렸던 지문 3개를 더해 8지문 × 2번 = 16문항. 같은 지문도 매번 조금씩 다르게 답하기 때문에 두 번씩 돌립니다. 맞음·부분·틀림은 사람이 판정합니다.

7과

어댑터 켜고 끄기 — LoRA 는 배운 일만 잘한다

어댑터를 붙인 모델은 배운 형식으로만 답하려 합니다. 다른 일을 시킬 때는 어댑터를 꺼야 합니다.

워커로 서비스하기 — 버튼 하나가 이 맥까지 오는 길

배포된 웹사이트에는 GPU 가 없습니다. 그래서 웹은 「할 일」을 적어 두기만 하고, GPU 가 있는 컴퓨터가 가져가서 만듭니다.

9과

역할 나누기와 큰 모델 — 형식은 LoRA, 독해는 큰 모델

한 모델에게 다 시키지 않고, 잘하는 일을 나눠 맡깁니다. 작은 LoRA 는 「문항 모양」을, 큰 모델은 「글 읽기」를 맡습니다.

7B LoRA 는 우리 문항 3,049개로 형식을 배웠습니다. 선지 5개, ①~⑤ 정답, 한국어 해설 같은 모양이요. 하지만 글을 깊이 읽는 힘은 LoRA 가 아니라 원래 모델(베이스)의 크기에서 나옵니다. 그래서 「이 글의 핵심 주장이 뭔가」「이 선지가 필자가 반박하는 관점인가」처럼 독해가 필요한 단계만 350억 개짜리 큰 모델에게 넘겼습니다. 문항 초안은 여전히 7B LoRA 가 씁니다.

10과

제목·주장도 가르치기 — 같은 요리법, 다른 재료

주제에서 통한 방법을 그대로 제목·주장에 옮겼습니다. 바뀐 건 학습 데이터뿐이고, 모델·LoRA 설정·파이프라인 모양은 같습니다.

유형마다 DB 에 있는 완료 문항을 「지시문 + 지문 → 문항 JSON」 쌍으로 뽑아(3과) 7B 에 3,000단계씩 LoRA 를 붙였습니다. 한 번에 한 유형씩, 맥을 켜 둔 채 잠들지 않게(caffeinate) 돌렸어요. 학습이 끝나면 새 어댑터로 바꿔 끼우고, 옛것은 날짜를 붙여 남겨 둡니다 — 새 게 더 못하면 되돌릴 수 있게요.

학습하는 동안 워커로 문항을 만들면 106초가 걸렸습니다(평소 13~20초). GPU 하나를 학습과 생성이 나눠 쓰기 때문이에요. 학습은 문항을 안 만드는 시간에 돌리는 게 좋습니다.

11과

오답을 하나씩 심사하기 — 모델이 모델을 채점할 때

오답 네 개를 한 덩어리로 「괜찮냐」고 묻지 말고, 하나씩 판정해서 문제 있는 것만 고칩니다. 그리고 완성된 문항을 학생처럼 한 번 풀어 봅니다.

웹에서 만든 31번 제목·주제 문항에서 정답과 같은 뜻의 오답이 나왔습니다. 학생이 「이것도 정답 아닌가요?」 할 문항이에요. 원인은 검사 방식이었습니다. 예전엔 오답 넷을 통째로 「합격/불합격」만 받고, 불합격이면 넷을 전부 다시 쓰게 했어요. 그러다 세 번째엔 판정과 상관없이 그냥 통과시켰습니다. 멀쩡한 오답까지 계속 갈아엎다가, 결국 문제 있는 걸 내보낸 셈이죠.

이렇게 모델에게 다른 모델(또는 자기)의 답을 채점시키는 걸 LLM-as-a-judge라고 합니다. 요령은 사람 채점과 같아요. 채점 기준을 몇 가지 칸(ok / also_correct / duplicate / off_topic)으로 정해 주고, 한 번에 한 가지씩 보게 하면 판정이 훨씬 안정됩니다. 「전체적으로 괜찮아?」 같은 질문은 모델도 대충 답합니다.

모의 풀이는 다른 각도의 검사입니다. 오답을 하나씩 볼 땐 괜찮아 보여도, 정답 옆에 나란히 놓으면 「이게 더 나은데?」가 되는 경우가 있거든요. 그래서 정답을 알려 주지 않고 35B 에게 문제를 풀게 해서, 다른 번호를 고르거나 「이것도 정답 가능」이라고 하면 경고만 남깁니다. 풀이 결과로 문항을 고치지는 않아요 — 판정이 틀릴 수도 있어서, 최종 판단은 사람이 하게 둡니다.

한 문항씩 한 번만 돌린 결과라 운의 몫이 있습니다. 같은 코드로 두 번 돌렸을 때 주제 3문항이 맞음↔부분으로 오갔어요. 그래서 「주장 5 → 17」처럼 크게 바뀐 것만 확실한 개선으로 봅니다.

① 가장 큰 병 — 주장: 지시문이 너무 세면 모델이 지어낸다. 주장 단계엔 윈도우 시절 규칙이 남아 있었습니다. 「정답은 필자의 논지에서 구체적 실천으로 한 단계 내려가야 한다, 논지 + should 는 불합격」. 작은 0.5B 가 주제문에 should 만 붙이는 걸 막으려던 규칙인데, 똑똑한 35B 검증기는 이걸 곧이곧대로 적용했어요. 「We should move our bodies」를 「구체적이지 않다」고 떨어뜨리고, 지문에 없는 행동을 붙여 고쳐 준 겁니다.

21번 전Individuals should schedule at least 30 minutes of brisk walking or stretching daily …
38번 전Governments should implement unified legal frameworks for metrology and establish …
20번 전(생성 실패 — 고친 문장이 20단어를 넘어 형식 검사에서 세 번 다 떨어짐)
20번 후We should prioritize learner engagement over entertainment in learning games.

실제 수능 주장 정답은 「필자의 주장 + should」 그대로입니다. 지시문을 그렇게 바꾸고, 검증은 지문 근거가 있나(grounded)와 필자 편인가(matches_author) 두 가지만 보게 했어요. 여기에 코드 검사 둘을 더했습니다. 7~16단어가 아니면 버리고, 주어가 지문에 없는 말(Governments, Educational institutions)이면 버립니다. 교훈은 이렇습니다. 작은 모델의 버릇을 막으려고 만든 규칙은 모델을 바꾸면 다시 봐야 합니다. 큰 모델은 규칙을 더 성실하게 지켜서, 틀린 규칙이 더 크게 틀린 결과를 냅니다.

고친 첫 판에선 18지문 중 8개가 2초 만에 실패했습니다. 35B 가 「JSON 으로」라는 말을 무시하고 문장 한 줄만 돌려줬기 때문이에요. 9과의 해설 사례와 같은 병이라, 한 줄 문장도 받도록 고쳤습니다. 받는 코드를 넉넉하게는 단계마다 챙겨야 합니다.

② 정답 모양 — 명사구·헤드라인은 코드가 본다. 주제 정답이 「mathematics focuses on patterns …」처럼 문장으로 나왔습니다(29·36번). 제목은 「Leaf-cutter ants cultivate fungus as food, demonstrating ….」처럼 마침표 달린 문장이었어요(39번). 검증기는 뜻만 봤고, 끝까지 못 고치면 핵심 메시지 문장을 그대로 정답 자리에 넣었기 때문입니다. 12과처럼 코드 규칙을 만들었습니다. 주제는 how·that 같은 절 머리 없이 동사(is·focuses·explains …)가 나오면 문장으로 봅니다. 제목은 마침표로 끝나거나 주요 단어 대문자가 60% 미만이면 헤드라인이 아닌 걸로 봅니다. 고친 뒤 이런 문장 모양 정답은 0개가 됐습니다.

③ 모의 풀이를 경고에서 판정으로. 제목 정답이 사례 하나로 좁게 잡힌 경우(35·37·38번)에, 정답을 모르고 푼 35B 는 세 번 모두 글 전체를 담은 다른 선지를 골랐습니다. 그래서 풀이가 다른 번호를 고르면 두 선지를 나란히 놓고 「어느 쪽이 글 전체를 담나」를 한 번 더 묻습니다. 이때 순서를 바꿔 두 번 묻고, 두 번 다 같은 쪽을 고를 때만 정답을 옮깁니다. 모델은 먼저 본 쪽(또는 나중 본 쪽)을 편애하는 버릇이 있어서(위치 편향, position bias) 한 번만 물으면 순서가 답을 정해 버리거든요.

마지막 판에서 정답이 옮겨진 건 1번(제목 20번), 두 판정이 엇갈려 경고만 남은 건 37번이었습니다. 옮겨질 때도 관리자 화면에 「정답을 ②에서 ③으로 옮겼습니다 — 확인 권장」이 뜹니다.

④ 겹치는 오답 — 단어 겹침으로 센다. 주장 30번 오답 넷이 모두 「It is important to keep paragraphs short …」였는데, 35B 심사관은 놓쳤습니다. 오답끼리 내용어(the·should 같은 말을 뺀 단어)가 70% 이상 겹치면 같은 오답으로 보고 새로 쓰게 했어요. 기준을 정하려고 마지막 판 오답 쌍을 전부 재 봤습니다. 진짜 겹친 두 쌍은 0.86·0.71이었고, 서로 다른 오답은 0.6 이하였어요. 정답과의 겹침은 재지 않습니다. 반대 방향 오답(「재미를 몰입보다 우선하라」)은 원래 정답과 단어를 많이 나눠 쓰니까요.

30번 전keep paragraphs short to make writing inviting · … so that readers can … · … so that readers never feel … (×2)
30번 후Writers should avoid every small pause … · Journalists should print every article in a single wide column · …

⑤ 이 시험지를 고정한다. 54문항을 저장소(ml/eval)에 고정 시험지로 남겼습니다. 지문 번호와 함께 지문마다 채점 기준(「이 글의 요지는 무엇인가」 한 줄)과 알려진 함정(실제로 틀렸던 모양)을 적어 뒀어요. 다음에 누가 채점해도 같은 잣대를 대게 하려는 겁니다. 지문 원문은 넣지 않고 DB 에서 읽습니다. 사람이 채점하기 전에 코드가 먼저 세는 자동 지표도 붙였습니다 — 생성 성공률, 시간, 경고 수, 정답 이동, 모양 틀린 정답, 겹치는 오답 쌍.

퍼센트 성적표 — 느낌 대신 숫자로, 그리고 숫자의 오차까지

「좋아진 것 같다」는 믿을 수 없습니다. 같은 시험지를 같은 방식으로 채점해 %로 적고, 그 %가 얼마나 흔들리는 숫자인지도 같이 봅니다.

13과의 고정 시험지(18지문 × 3유형)를 버전마다 2번씩 돌려 108문항씩 쌓았습니다. 숫자는 두 종류입니다. 정답 적절률은 사람(여기선 제가)이 지문마다 적어 둔 「요지 한 줄」에 대어 채점합니다. 오답 품질은 사람 대신 35B 를 온도 0으로 고정해 모든 버전의 오답을 같은 문구로 다시 판정합니다(judge_distractors.py). 파이프라인 안의 판정은 버전마다 규칙이 달라 비교가 안 되니, 재는 자는 따로 둔 것이에요. 시험 감독과 채점 위원을 분리하는 것과 같습니다.

① 숫자에도 오차가 있다. 이번에 가장 크게 배운 건 이겁니다. 주제 정답 적절률은 같은 코드인데도 한 번 돌렸을 땐 88.9%, 두 번 돌렸을 땐 75.0%가 나왔어요. 모델이 매번 조금씩 다르게 쓰니까(온도 0.3) 시험을 몇 번 보느냐에 따라 점수가 흔들립니다. 문항이 108개일 때 85% 근처 점수는 대략 ±7%p까지 운으로 오갑니다(표준오차 √(0.85×0.15/108) ≈ 3.4%p의 두 배). 그래서

「이번에 고친 것이 건드릴 수 있는 숫자인가」를 먼저 생각하면, 우연히 오른 숫자를 성과로 착각하지 않습니다.

② 이번에 고친 것 — 너무 쉬운 오답. 35B 판정에서 「지문과 무관(off_topic)」한 오답은 예전엔 그대로 뒀습니다. 수능에도 하나쯤은 있으니까요. 그런데 성적표를 뽑아 보니 세 문항 중 하나(31.5%)에 무관 오답이 2개 이상이라, 학생이 지문을 안 읽고도 답을 좁힐 수 있었어요. 이제 무관 오답은 문항당 1개까지만 남기고, 나머지는 「한 사례만 다룸·과장·반대·필자가 반박하는 통념·같은 소재의 다른 주장」 중 하나로 다시 쓰게 합니다.

전the historical development of the English language · the economic costs of preserving cultural diversity (23번 주제)
후the danger that a species faces when it loses all variation · the role of natural selection in preserving a species

③ 대가 — 그럴듯한 오답은 정답에 가까워진다. 주제에서 「정답으로도 읽히는 오답」이 0.7% → 4.2%(144개 중 1개 → 6개)로 늘었습니다. 오답을 지문 쪽으로 끌어당기면 정답과의 거리도 줄어드는 게 당연하죠. 전체로는 2.8% → 3.0%로 거의 그대로이고, 그런 문항은 모의 풀이 경고가 붙으니 관리자가 볼 수 있습니다. 하나를 올리면 다른 게 움직이는지 같이 재는 것이 성적표를 여러 줄로 만든 이유예요.

문항당 시간이 13.8초 → 15.5초로 늘었습니다. 무관 오답을 다시 쓰느라 35B 호출이 늘었기 때문이에요.

덤 — 영상 로드맵에서 우리는 어디쯤? 「나만의 LLM 바닥부터 만들기」 영상의 3단계(데이터·구조 → 사전학습 → 파인튜닝) 중 우리는 3단계만 합니다. 1·2단계는 알리바바가 수조 개 토큰으로 이미 해 둔 Qwen 을 가져다 쓰고(영상의 「치트키」), 거기에 LoRA 로 문항 쓰는 특기를 가르치는 거예요(4과). 영상의 「질문은 가리고 답만 맞추게 하는 마스킹」은 우리 학습에도 들어 있습니다 — --mask-prompt. 지문(질문)까지 외우게 하면 문항 JSON(답)을 배우는 데 쓸 힘이 지문 베끼기로 새니까요(3과). 영상의 「온도(temperature)로 가끔 확률 낮은 단어도 내게 한다」는 우리 초안 온도 0.3, 채점·재판정은 0 입니다. 같은 문항을 다시 돌리면 조금씩 다른 이유가 이 0.3 이고, 재는 자는 흔들리면 안 되니 0 으로 둡니다(①).

새 유형 붙이기 — 내용일치는 「판단」이 아니라 「사실 확인」

주제·제목·주장에서 쌓은 틀(데이터 → LoRA → 파이프라인 → 워커 → 시험지)에 네 번째 유형을 끼웠습니다. 새로 배운 건 셋입니다. 유형끼리 어댑터를 나눠 쓰기, 모델에게 쓸데없는 일 안 시키기, 사실 문제는 사실로 채점하기.

① 데이터 — 걸러 낸 줄 알았는데 3/4을 버리고 있었다. DB 에 완료된 영어 일치·불일치 문항이 2만 4천 개 있는데, 처음 뽑았을 땐 5,674개만 남았어요. 이유를 세 보니 18,576개가 선지를 ### 대신 줄바꿈으로 나눈 예전 형식이었습니다. 좋은 문항이 형식 때문에 통째로 빠진 거죠. 줄바꿈도 받게 고치자 23,788개가 살아났고, 같은 지문에서 비슷한 문항이 몰리지 않게 지문·유형당 3개씩 골라 13,288개(2,515지문)로 학습했습니다. 데이터를 거를 땐 「왜 빠졌나」를 세어 보는 게 첫 번째 확인이에요.

② LoRA 하나로 두 유형. 일치와 불일치는 거울상입니다(정답이 「맞는 1개」냐 「틀린 1개」냐). 그래서 어댑터를 둘 두지 않고 하나로 배우게 하고, 사용자 메시지 첫 줄 [유형] 일치 / [유형] 불일치로 구분했어요. 맥 런타임은 어댑터마다 모델 한 벌(4.3GB)을 따로 올리니(9과), 하나로 합치면 메모리 4.3GB 를 아낍니다. 지금 워커는 7B 원본 + 어댑터 4개 + 35B 로 약 40GB 입니다.

③ 모델에게 복사를 시키지 않기. 기존 세 유형은 학습 데이터의 답(JSON)에 지문(Paragraph)이 통째로 들어 있어서, 모델이 문항을 쓸 때마다 지문 200단어를 한 글자씩 다시 옮겨 적었습니다. 생성은 한 토큰씩이라 그게 몇 초예요. 새 유형은 답에서 지문을 빼고, 지문은 프로그램이 채웁니다. 모델은 새로 만들어야 하는 것만 쓰게 하는 게 속도의 기본입니다.

② 20분 멈춘 문항. 측정 도중 한 문항이 20분 넘게 끝나지 않았습니다. 처음엔 「다시 쓰기가 너무 많이 반복된다」고 보고 문항당 시간 한도(150초)와 호출 수 상한을 넣었는데, 그래도 또 멈췄어요. 그래서 짐작을 멈추고 프로세스 안을 들여다봤습니다(macOS sample — 몇 초간 프로그램이 어디서 시간을 쓰는지 찍어 줌). 모델(GPU)이 아니라 파이썬이 문자열 포함 검사(in)만 끝없이 하고 있었어요.

버그while s[:1] in "①②③④⑤": s = s[1:]
고침while s and s[0] in "①②③④⑤": s = s[1:]

선지 앞 번호를 떼는 코드인데, 모델이 드물게 번호만 있는 선지(「①」)를 내면 s 가 빈 문자열이 되고, 파이썬에서 빈 문자열은 어떤 문자열에도 「들어 있다」고 나옵니다('' in "①②③" 이 참). 그래서 영원히 돌았어요. 운영 중인 워커도 같은 코드라, 웹에서 일치·빈칸 문항이 드물게 멈출 수 있었습니다. 고치고 워커를 다시 켰어요. 교훈은 둘입니다. 「느리다」는 짐작보다 들여다보기가 빠르다, 그리고 모델 출력은 가끔 이상한 모양으로 온다 — 받는 코드는 빈 값·번호만 있는 값까지 견뎌야 합니다(9과 「받는 코드를 넉넉하게」의 연장).

③ 정답이 빈칸의 원래 뜻과 같은가. v3 에서 드러난 두 결함(정답이 원래 구절과 다른 생각을 말함 · 빈칸 위치와 선지가 따로 놂)은 뿌리가 같았습니다 — 「정답 선지가 가린 구절과 같은 뜻인가」를 아무도 묻지 않았어요. 넣어 보기 판정은 「흐름에 맞나」만 보니, 문장과 동어반복이 되는 엉뚱한 정답도 통과했습니다. 그래서 초안 직후와 다시 쓰기 뒤 두 번 35B 에게 이걸 묻고, 아니라면 정답을 원문 구절 그대로로 바꿉니다. 원문 그대로인 정답은 틀릴 수가 없으니까요.

겨냥한 결함은 없앴지만 전체는 75% 근처를 맴돕니다. 남은 건 거의 한 종류예요 — 35번 정답 「목욕은 일주일에 한두 번까지」 옆에 오답 「최대 주 2회로 제한」처럼, 오답이 정답을 살짝 바꿔 쓴 말이라 정답으로도 읽힙니다. 35B 넣어 보기 판정은 이걸 「틀림」으로 봐서 거르지 못해요. 이런 결함이 실제 쓰임에서 얼마나 문제인지는 17과 실사용 지표가 쌓이면 보고, 그때 다시 손대기로 했습니다 — 시험지 점수가 제자리를 맴돌면, 실제 데이터를 보고 다음 수를 고르는 편이 낫습니다.

19과

순서·삽입 — 학습 없이 규칙으로 만들고, 모델은 채점만

모든 문제를 모델에게 가르칠 필요는 없습니다. 규칙으로 만들 수 있는 문제는 규칙으로 만들고, 모델에게는 「풀 만한가」만 묻습니다.

순서 문항은 글을 도입 + 세 덩이로 자르고 섞으면 되고, 삽입 문항은 한 문장을 빼고 다섯 틈에 번호를 붙이면 됩니다. 문장을 새로 지을 일이 없으니 LoRA 학습이 필요 없어요. 학습실(/practice)에 이미 이 규칙 생성기가 있어서 파이썬으로 옮겼습니다 — 덩이를 자르고 문장을 뺄 때 연결 단서(However · This · For example …)가 있는 자리를 우선하고, 정답 번호는 먼저 고르게 뽑습니다.

규칙만으로는 순서가 두 가지로 읽히거나 주어진 문장이 두 곳에 다 들어가는 문항이 섞입니다. 그래서 시드를 바꿔 가며 여러 개를 만들고, 35B 가 정답을 모르는 채로 풀어서 「정답을 맞히고, 다른 답도 된다고 하지 않는」 첫 문항만 씁니다. 모델이 문제를 만드는 게 아니라 수험생 역할을 하는 거예요. 해설만 35B 가 씁니다.

20과

무관한문장·어휘·어법 — 「풀 수 있다」와 「옳다」는 다르다

원문을 한 곳만 고쳐 만드는 세 유형을 붙였습니다. 모의 풀이만으로는 부족했어요. 틀린 문항도 35B 는 잘 맞혔거든요. 그래서 「무엇이 틀릴 수 있나」를 하나씩 따로 물었습니다.

21과

요약 — 판정이 잡아도 다시 쓰기가 못 고치면 소용없다

요약문 완성은 빈칸과 같은 틀로 만들었습니다. LoRA 는 요약문 한 줄과 (A)(B) 쌍 다섯만 쓰고, 지문과 합치는 건 코드가 합니다. 네 번 고쳐 맞음 38.9 → 50% 안팎, 틀림 25 → 11%까지 왔지만 아직 다른 유형보다 낮습니다.

① 데이터 — 표기가 일곱 가지. 완료 8,213문항 중 처음 뽑힌 건 절반도 안 됐습니다. 선지 구분자가 – · - · … · …… · / · --- · ······로 제각각이고, (A)(B) 표시가 없는 선지가 2,655개, 요약문 앞을 빈 줄 대신 ###로 나눈 문항과 밑줄 없이 (A)만 둔 문항도 많았어요. 모두 「① (A) x – (B) y」와 「(A) ________」로 맞춰 6,332문항(2,756지문)으로 학습했습니다. 검증 손실 1.82 → 1.03.

② 정답이 둘 — 이번 유형의 주적. 오답 쌍이 정답 낱말의 유의어를 쓰면 정답이 둘이 됩니다(copying – resemble 옆 representation – depict, cultivated 옆 raised). 고친 순서가 교훈이에요.
